# Real-CXL throughput check — September 23, 2026

The current refactored Release binaries completed a two-remote-publisher, four-broker, replication-off append run with the shared region resident on the restored CPU-less NUMA node 2. The median of three independently started 10 GiB transfers was **8.874 decimal GB/s**. The paper's ORDER5/ACK1/RF0 bar is **11.130 decimal GB/s**, but this experiment used **one publisher thread per broker route** while the paper launcher defaults to **six** (`PaperScripts/run_fig1_throughput_scaling.sh`, `THREADS_THROUGHPUT`). The numerical 20.3% gap is therefore **not a matched performance comparison or evidence of a refactor regression**. The subsequent controlled local before/after study is documented in [the paired real-CXL review](2026-09-23-cxl-before-after.md).

Raw manifests and logs are under `/home/domin/Embarcadero/results/cxl-paper-local/embarcadero-dev-1002-<trial>/`. Each manifest records `status=passed`, exact per-client ACKs of 1,310,720 messages, nonzero traffic on all four brokers, zero process exit codes, completed remote cleanup, and removal of the owned shared-memory object. Each broker's 96 GiB shared mapping had 25,165,824 resident 4 KiB pages on node 2; the runner validated this from `/proc/<pid>/numa_maps`. This establishes CXL-node placement through the kernel's NUMA topology; the runner does not establish the precise PCI device identity of each page. The host reports a 256 GiB CXL decoder window and a Type-3 device.

The tested cell uses two remote clients (`c1` and `c3`), 5 GiB each, 4 KiB messages, 2 MiB batches, one thread per broker route, four brokers and the sequencer on host A, 500 µs ORDER5 epochs, ACK1 and replication factor zero. Brokers were pinned to host-A NUMA node 1, the clients to their NIC-local nodes (`c1` node 0; `c3` node 1), and the 96 GiB real-backend shared region to node 2. A fixed common virtual base was used after an automatic-base attempt failed during follower mapping before publishing. The measured interval starts at each client's push barrier and ends at its authoritative ACK completion; the aggregate uses the earliest start and latest end. Client durations are logged to 0.01 s, and cross-host wall-clock aggregation depends on NTP synchronization (c3 root dispersion observed at roughly 9 ms). There was no subscriber payload audit inside the timed run; a separate real-CXL 10 GiB audited local-client run passed exact ordered delivery, and its rate is not treated as a paper comparison.

The paper specifies two remote publishers with Xeon 8462Y+ and 8592+ hosts and MTU 9000. The available `c1` is instead a Xeon 8280M host with a 100 GbE NIC on PCIe 3.0 x8; the available `c3` matches the 8592+ CPU but its 100 GbE NIC currently has **MTU 1500**. `c3` was the slower publisher in all three trials. No NIC configuration was changed. The candidate is a refactored revision, and the paper does not give its mapped-region size. The thread-count mismatch, these hardware differences, and ordinary run variation prevent attributing the numerical gap to CXL hardware, source changes, or any single network setting.

Three separate real-CXL **local-client** 10 GiB ACK-only trials, with the client on host-A NUMA node 0 and four brokers on node 1, measured 3.728, 3.782, and 3.707 decimal GB/s (median **3.728 GB/s**) at **one publisher thread per broker route**. The mapping was on node 2, and each run passed exact ACK and four-broker routing checks. An additional audited local-client run passed all 2,621,440 indexed 4 KiB messages; its publish and end-to-end goodputs were 3.692 and 3.569 decimal GB/s. These are one-client TCP loopback measurements, not the paper's two-remote-publisher experiment or its separately reported single-remote-publisher control. A co-located client does not bypass the client-to-broker TCP path in this runner, so the local result is not a measured CXL-only upper bound. The historical local launcher used **four** threads per broker route; with that setting, the current broker measured **11.23 GB/s median** in the matched study, so 3.728 GB/s is an underprovisioned diagnostic, not representative local throughput of the refactored broker.

The paper's 7.184 GB/s two-copy DRAM bar and 1.366 GB/s durable bar use stronger completion contracts and are not direct comparators. Its 14.906 GB/s CXL-side ceiling also includes a third remote and a local publisher, so it is a different topology. A matched refactor regression verdict requires the old and new binaries run on the same current hardware with the same NIC MTU, client hosts, mapping, build contract, and measurement protocol.
