# Real-CXL throughput check — September 23, 2026

The current refactored Release binaries completed a two-remote-publisher, four-broker, replication-off append run with the shared region resident on the restored CPU-less NUMA node 2. The median of three independently started 10 GiB transfers was **8.874 decimal GB/s**. The paper's ORDER5/ACK1/RF0 bar is **11.130 decimal GB/s**, but this experiment used **one publisher thread per broker route** while the paper launcher defaults to **six** (`PaperScripts/run_fig1_throughput_scaling.sh`, `THREADS_THROUGHPUT`). The numerical 20.3% gap is therefore **not a matched performance comparison or evidence of a refactor regression**. The subsequent controlled local before/after study is documented in [the paired real-CXL review](2026-09-23-cxl-before-after.md). A September 24 six-thread remote follow-up and paired old/new broker comparison appear below.

## Six-thread remote follow-up, September 24

We inventoried the actual data path before repeating the paper-shaped run. Host A has an AMD EPYC 9754 and a 100 GbE ConnectX-5 at PCIe 3.0 x16, MTU 9000. `c1` has a Xeon 8280M and ConnectX-5 at PCIe 3.0 x8, MTU 9000; `c3` has a Xeon 8592+ and ConnectX-5 at PCIe 3.0 x16, **MTU 1500**. All three NICs negotiated 100 Gb/s. The clients used the 10.10.10.x data addresses and NIC-local CPU nodes; brokers stayed on host-A node 1 and the 96 GiB region on real CXL node 2. `c2` is another 8280M/ConnectX-5 host with MTU 1500, so it is not a closer paper match; `c4` remained unreachable. No NIC setting was changed. Six-stream `iperf3` tests gave about 5.94 GB/s to `c1` and 8.05 GB/s to `c3` individually; simultaneous tests gave 5.71 and 6.06 GB/s, or 11.77 GB/s aggregate. These are raw TCP diagnostics, not Embarcadero throughput or a strict upper bound for its timing method.

The corrected workload used **six publisher threads per broker route** from each of two clients, 5 GiB per client in 4 KiB messages and 2 MiB batches, four brokers, ORDER5/ACK1/RF0, and 10 GiB total. Its profile required `network.io_threads=16`: each receive thread owns one publish socket for its lifetime, so the previous setting of six could not serve the twelve client-to-broker sockets. An initial six-thread setup failed to become ready with that insufficient setting; it was cleaned and excluded. Another setup attempt omitted the remote-reachable head address and also failed before measurement. Both failed attempts remain in the result directory. The client pool cap was 2 GiB so the required batch slots fit without violating its limit. Three independent qualified runs with the fixed broker and the same AMD-built client measured **10.130, 9.761, and 9.761 decimal GB/s** (median **9.761 GB/s**). Each passed exact 1,310,720 ACKs per client, all four broker routes, zero retransmit/fence checks, executable SHA checks, node-2 placement, normal exit, and owned-resource cleanup. The index is `/home/domin/Embarcadero/results/cxl-paper-local/remote-threads6-current-index.json`.

To test the client-binary concern, we built the same clean source revision (`cfbad229`) in isolated directories on `c1` and `c3`, using Release and native architecture flags. The old dirty remote checkouts were untouched. The remotely compiled clients were verified by SHA256 before launch and through `/proc/<pid>/exe`; the broker binary and workload remained fixed. In two adjacent AB/BA pairs, the native/AMD-built throughput ratios were approximately **1.028** and **1.000**, with geometric mean **1.014**. This small, noisy sample does not isolate ISA flags from compiler differences and cannot explain the roughly 12% gap to the paper bar. The index is `/home/domin/Embarcadero/results/cxl-paper-local/remote-native-abba-index.json`.

Finally, we compared the retained pre-refactor broker (`ae9959dd`, SHA256 `19455cc1becd5f95157f493acda5114709189222160a2542a1517aea7f5423a5`) with the fixed broker (`f754c906`, SHA256 `db1559d22829e644c1f9ee4510e1f8c7e3bedf1098e49204ffae4e3d45ab9532`), holding the AMD-built current client binary (SHA256 `1e025ae3c9ca30f0d575490026c455652c95ee66491c16f13d17551c576cccc6`) and all settings constant. The old broker lacks `--print-layout`, so its harness used the fixed layout calculator for preflight and verified the actual old-broker startup and CXL placement. One qualification run passed, followed by three adjacent AB/BA pairs; all six paired trials passed the same strict checks.

Until then, the evidence supports maintained refactor throughput on this remote setup, not equivalence to the published platform.

## `c3` jumbo-frame and HugeTLB follow-up, September 24

We changed only `c3`'s dedicated 10.10.10.x interface (`ens801f0np0`) from MTU 1500 to **9000**. Host A was already at 9000. Both directions passed three 8972-byte, don't-fragment pings, verifying a complete 9000-byte IP packet on the test path. The active NetworkManager connection `embar-100g` (UUID `29ef017d-e98b-481b-820d-b3d1d8b420d3`) now stores MTU 9000, so reconnecting the interface should preserve it. We did not alter the management interface, TCP sysctls, NIC rings, interrupt policy, or offloads; the latter were already enabled and the data NIC reported zero RX errors or drops after the trials. The pre-change profile had MTU `auto`; it and the runtime interface can be restored with `sudo nmcli connection modify 29ef017d-e98b-481b-820d-b3d1d8b420d3 802-3-ethernet.mtu auto` and `sudo ip link set dev ens801f0np0 mtu 1500` on `c3`.

The six-thread client's batch pool needs 1,612,808,320 bytes. Earlier trials explicitly set `EMBAR_USE_HUGETLB=0` and used the THP fallback. For a separate HugeTLB control, we reserved **1024 × 2 MiB pages** on `c3` NUMA node 1 (the NIC-local node) and set runtime `vm.hugetlb_shm_group=1001` for the client user. The client log confirms `MAP_HUGETLB success` for a 1,614,807,040-byte mapping; node 0 retained zero reserved pages, and all 1024 node-1 pages were free again after the run. These hugepage and group settings are **runtime only**, unlike the NetworkManager MTU profile; reapply them after reboot if needed. The original values were zero pages and group 0. To release the reserved pool after experiments, write `0` to `/sys/devices/system/node/node1/hugepages/hugepages-2048kB/nr_hugepages` and set `vm.hugetlb_shm_group=0` on `c3`, once no client is using the pages.

One initial MTU-only transfer completed exact ACKs, but the harness rejected it because broker 0 exceeded the original ten-second *post-measurement shutdown* grace and was force-killed. It is excluded. We extended only that shutdown grace to 30 seconds for six subsequent qualified trials, arranged as three adjacent MTU-only/HugeTLB pairs; every trial passed exact per-client ACKs, all routes, zero client retry/fence, normal broker/client exit, node-2 CXL placement, binary identity, and owned-resource cleanup. Both variants kept the broker binary and AMD-built client binary fixed; only `c3`'s `EMBAR_USE_HUGETLB` flag changed between variants. The full index and script hashes are under `/home/domin/Embarcadero/results/cxl-paper-local/c3-tuning-20260924/paired-mtu-huge-index.json`.

The HugeTLB/THP paired geometric ratio was **1.027**, with a wide two-sided Student-t 95% interval of roughly **0.927–1.139** over only three pairs. HugeTLB clearly worked, but these aggregate results do not establish a throughput gain. `c3` finished its 5 GiB in 0.85–0.98 seconds; `c1` took 1.07–1.15 seconds in every trial, so `c1` determined the two-client finish. The pre-MTU fixed-broker median was 9.761 GB/s and the new MTU-only median was 9.851 GB/s, but those are not adjacent old/new MTU pairs and do not establish an application-level jumbo-frame effect. Client-reported durations have 0.01-second precision.

To verify the NIC path separately, we repeated the same four-second, six-stream `iperf3` diagnostics. `c3` alone improved from **8.05 to 12.32 GB/s** received on host A. With `c1` transmitting simultaneously, `c3` improved from **6.06 to 6.92 GB/s** and the two-client raw TCP sum from **11.77 to 12.75 GB/s**. These show that MTU 1500 had materially constrained `c3`'s TCP path, while the application's aggregate completion still depends on the slower `c1` and its older PCIe x8 platform. Raw TCP rates and Embarcadero ACK-completion rates use different work and timing, so they should not be equated. The next paper-fidelity step remains a paper-class second publisher (`c4` if reachable), with the six-thread application profile and strict binary/ACK checks repeated on both sides.

For a final configured-state check, we used the clean-source, Intel-native client binaries on both hosts. `c1` already had 8,200 free 2 MiB HugeTLB pages on its NIC-local node 0, but the earlier diagnostic runner had disabled HugeTLB there; we set its runtime `vm.hugetlb_shm_group` from 0 to 1001 and enabled HugeTLB for both clients. Three identical 10 GiB, six-thread runs passed at **10.130, 9.851, and 10.035 GB/s** (median **10.035 GB/s**). Both remote logs confirmed successful HugeTLB mappings in every run; all exact-ACK, routing, CXL-placement, binary-identity, exit, and cleanup checks passed. The index is `/home/domin/Embarcadero/results/cxl-paper-local/c3-tuning-20260924/native-bothhuge-index.json`. One preceding native run with HugeTLB on `c3` only passed at **9.099 GB/s** because `c1` took 1.18 seconds; it is not a paired estimate of the effect of enabling `c1` HugeTLB. `c1` still determined completion in all three final runs (1.06–1.09 seconds versus `c3`'s 0.87–0.89). Its preexisting page reservation was not changed, and its group setting is runtime only; reset with `sudo sysctl -w vm.hugetlb_shm_group=0` on `c1` if no more client tests need it. The configured-state median is about **90.2%** of the paper's 11.130 GB/s bar, but the publisher hardware and timing remain different, so this is not a paper reproduction or a demonstrated tuning gain.
